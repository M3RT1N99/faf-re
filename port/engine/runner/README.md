# port/engine/runner — the headless replay runner on Android

Milestones M3b (link) and M3c (run) of the [roadmap](../../../docs/port/android-roadmap.md): the
code that runs `main.exe /headlessreplay` on Windows
([headless-replay.md](../../../docs/port/headless-replay.md)), `moho::HEADLESS_RunReplay` and
everything it reaches, linked for Android into

- `libfafengine.so`, the engine: every TU of the closure as a whole object, `-Wl,--no-undefined`,
  libc++ static, `-lz -llog`, linked with `--wrap` for the pthread functions of the low arena;
- `faf_headless_runner`, a small executable with the low arena
  ([port/engine/lowarena](../lowarena/README.md)): it loads `libfafengine.so` from its own
  directory (or `$FAF_ENGINE_LIB`) into a range below 2 GB, calls `faf_headless_main(argc, argv)`
  on a thread with a low stack and returns its exit code. Since release 0.4.0 it also reads
  `.fafreplay` files itself, has `/replayinfo` and `/convertreplay` modes and reports crashes
  ([below](#release-040-replay-input-and-crash-reports)); the APK ships it as
  `lib/<abi>/libfafrunner.so` for the in-app replay test.

The command line is main.exe's: `faf_headless_runner /headlessreplay <file> /init <init_faf.lua> ...`
(the leading `/headlessreplay` may be left out). On a device or the emulator,
`scripts/port/run_runner_android.py` does all of it in one command (below).

| File | What it is |
|---|---|
| `closure.txt` | The TUs `libfafengine.so` links, generated by `scripts/port/link_closure.py`; do not edit by hand |
| `RunnerMain.cpp` | `faf_headless_main` (in the .so: sets `__argc`/`__argv`, calls `HEADLESS_RunReplay`) and, with `FAF_RUNNER_EXECUTABLE`, the executable's `main` (low arena, low load, engine thread) |
| `MeshSpatialDb.cpp` | The engine's spatial database templates from `moho/mesh/Mesh.cpp` (compiled with `FAF_PORT_MESH_SPATIAL_DB_ONLY`, which leaves the D3D9 mesh renderer out): real engine code, which the .scmap load needs |
| `HeadlessStubs*.cpp` | Runner-only stand-ins for user-side code (UI, render, audio, wx, live networking, the user session, the D3D texture resource without a device), never part of main.exe; plus a few traps (below) |
| `ReplayFile.{h,cpp}` | Executable only (0.4.0): `.fafreplay` decoding (zstd from [port/third_party/zstd](../../third_party/zstd/README.md), legacy base64+zlib from the system libz), the version rewrite to 3764, the header scan, `/replayinfo`'s JSON, SHA-256 |
| `RunnerCrash.{h,cpp}` | Executable only (0.4.0): the crash reporter for fatal signals |

## Building

```sh
python scripts/port/link_closure.py            # only when the engine's references change (needs the Debug|Win32 objects)
python scripts/port/build_runner.py            # arm64-v8a into buildstage/runner/arm64-v8a
python scripts/port/build_runner.py --abi x86_64
```

`build_runner.py` compiles each TU with the arm64 sweep's command (`scripts/port/engine_sweep.py`:
main.vcxproj's Release|x64 defines and include directories, `port/engine/shim`,
`port/engine/compile_flags.txt`) plus `-fPIC -ffunction-sections -fdata-sections -g`, the
runner's own sources (`port/engine/runner/*.cpp` except the executable-only `ReplayFile.cpp` and
`RunnerCrash.cpp`, which are compiled with the low arena's plain flags, `RUNNER_EXE_SOURCES`, together
with the vendored zstd decoder, `ZSTD_SOURCES`; the executable links `-lz`), and the WildMagic
Foundation TUs the closure lists, from the local, gitignored `dependencies/WildMagic3p8`. Wild Magic needs two stand-ins,
generated into `<out>/wm3-include`: `<sys/timeb.h>` (bionic has none) and copies of
`Wm3Query{2,3}Filtered.{h,inl}` that call the dependent base's `Det2/3/4` through `this->`.
Compiling is incremental (a TU is skipped while its command and every file it includes are
unchanged; a TU that stopped on a missing header has no dependency file and is retried): a full
build takes about 2 minutes on 18 jobs, a run with nothing changed about 15 s including the link
and the report.

| Option | |
|---|---|
| `--abi arm64-v8a\|x86_64` | target, default arm64-v8a (`aarch64-linux-android26`) |
| `--out DIR` | build directory, default `buildstage/runner/<abi>`. Several builds can run side by side, each in its own directory; when several people or agents iterate at once, each uses its own `--out` and leaves the default directory as the shared seed |
| `--seed DIR` | copy every up-to-date object from DIR first (default: the ABI's default directory when `--out` is another one), so a new directory does not start from zero |
| `--files GLOB...` | recompile only these TUs (closure TUs, runner sources, WildMagic TUs; paths or globs relative to `src/sdk`) and relink with the objects already there |
| `--force`, `--link-only`, `--no-link` | recompile everything; only link; only compile |
| `--jobs N`, `--extra ARG`, `--ldflag ARG` | parallel compilers; one more compile or link argument (repeatable) |

Output in the build directory: `libfafengine.so`, `faf_headless_runner`, `report.md`,
`results.json`, `link.log`, and per TU `obj/<tu>.o` (with its dependency file and a stamp) and
`logs/<tu>.log`. The exit code is 0 only when both binaries linked.

`report.md` lists the compile failures (first error, class, owning component), the undefined
symbols grouped by the TU that defines them on Windows and by the TUs that reference them, and the
duplicate symbols with both definitions. lld stops after duplicate definitions, so a second link
that tolerates them (into a scratch file, deleted again) collects the undefined symbols; both are
in `link.log`. Owners come from the Win32 objects (`link_closure.py`'s index of qualified names;
a vtable or typeinfo belongs to its class's key-function TU).

## The closure

`link_closure.py` reads the Debug|Win32 objects (`buildstage/main/Win32/Debug`, ObjectFileName
overrides resolved from main.vcxproj), WildMagic's Foundation objects and the symbol tables of the
libraries the Windows link uses, and writes `closure.txt` plus a report
(`buildstage/runner/closure/report.md`, `closure.json`). `--check` exits 1 when `closure.txt` is
out of date. The arm64 compile status comes from an engine sweep (default
`buildstage/engine-sweep/m3b`, the sweep after the M3b ports; M2's was `buildstage/engine-sweep/final`).
Since M3c the closure is computed from the post-M3b sweep: `UserUnit`, `CLobby`,
`CUserSoundManager`, `CSaveGameRequestImpl` and the other user-side TUs that compile since M3b are
linked as real code instead of stand-ins.

- **Roots:** the TU that defines `HEADLESS_RunReplay`, plus every TU with a static initialiser
  that registers something and can be linked, plus every other non-user-side TU with a static
  initialiser of any kind (variant `init`). Registration kinds: Lua binders, RTypes
  (`PreRegisterRType`/`.CRT$XCL`), console commands and variables (including `CConFunc`),
  serializer and construct helpers (`SerHelperBase`), prefetch kinds and resource factories. On
  ELF a TU's initialisers only run when its object is linked; a missing one fails silently, so the
  closure takes them all. The report compares the narrower variants `lua` (Lua binders only) and
  `reg` (every registration kind), lists every registration TU left out with the reason (including
  `WinMain.cpp`, `ResolutionCommands.cpp` and `FrameDumpCommands.cpp`), and the linkable
  static-initialiser TUs that register nothing.
- **User side** (the stub rule): `moho/ui`, the renderer (`moho/render`, `gpg/gal`, mesh, terrain,
  particles, effect rendering), `moho/audio`, movies, `moho/app`, the wx Lua debugger windows, live
  networking, and the user session (`CWldSession`, `UserUnit`, `UserEntity`, `UserArmy`, ...).
  Never stubbed, whatever their directory: the runner itself and the session loader it drives, the
  TUs M3b ports (spec components P, W, N, and the integration's `moho/net/Common.cpp`, whose
  `NetSpeeds` times the sim driver, and `gpg/gal/Matrix.cpp`, whose `Math::mul` sim-side effect
  emitters call), and the sim-side TUs in user-side directories (sound requests, decal handles,
  effect emitters, `WaveSystem`/`Cartographic` and the decal manager `CWldSplat`/`CWldTerrainDecal`/
  `CDecalGroup`, which consume sections of the sequentially read .scmap stream).
- **Cut:** a user-side TU cannot be linked when it does not compile for arm64, calls wx, D3D,
  DirectSound or Winsock directly, or needs the vtable/typeinfo of a class whose key function lives
  in such a TU. A minimum cut over symbols finds the fewest user-side symbols whose stubs keep
  those TUs out; the user-side TUs that compile and do not drag one in are linked for real.
- **Itanium edges:** MSVC emits vftables and RTTI as COMDATs wherever they are used; the Itanium
  ABI emits them only with the class's key function. A TU that constructs a class or uses
  typeid/dynamic_cast/throw/catch on it therefore depends on Android on the TU defining the
  class's virtual functions, an edge the Win32 symbols do not show. `link_closure.py` adds it.
  Such an edge into an unlinkable TU cannot be stubbed; the referencing site needs a guard. The
  report lists these as `<vtable/typeinfo of ...>` cuts.

The report also lists the references into stubbed TUs (what `HeadlessStubs*.cpp` must define,
from the Win32 view; the arm64 link is authoritative), the closure TUs that call platform
libraries on Windows, the duplicate definitions MSVC's `/FORCE` hides, and the registration TUs
left out.

## Stand-ins, traps and port seams

What the Windows runner computes with user-side code it reaches, the Android runner computes the
same way or does not link at all. Three mechanisms, each checked against the real code and, where
it matters, against call chains recorded with an instrumented Debug|Win32 `main.exe` on T1-T3:

- **Stand-ins** (`HeadlessStubs*.cpp`, `FAF_RUNNER_STUB`): user-side functions whose real result in
  the Windows runner's state (no wx application, device, `CWldSession`, sound engine, UI or live
  networking) is known and trivial, usually null, false or nothing. Each cites the real definition
  and logs its first call as `[stub] <name>`.
- **Traps** (`FAF_RUNNER_TRAP`): user-side functions the Windows runner never calls and whose real
  result cannot be reproduced: `D3D_GetDevice` (the D3D9 device singleton) and `CHostManager`
  (reverse DNS behind `NET_GetHostName`, reached only from `/gpgnet` and LAN discovery). Reaching
  one logs `[stub] <name>` and ends the run through `gpg::Die`, so it can never cause a silent
  difference.
- **Port seams** in engine code, `#if defined(_WIN32)` so main.exe compiles what it did:
  - *No D3D9 device off Windows.* The Windows runner calls `D3D_GetDevice()` to create texture
    resources while it loads the map: `RWldMapPreviewChunk::Load`, `CWldTerrainRes::Load`
    (stratum masks, water map), `SetBackground`, `SetSkycube`, `AddEnvLookup` (`CWldMap.cpp`) and
    `CAnimTexture::LoadFramesFromBaseName` (decal frames); `UnitWeapon`'s `DoInstaHit` binder does
    the same in replays that use it, and `Sim_Create_exxt` asks the device for its viewport
    (`StartupHelpers.cpp`, Windows-only since M3b; null in the Windows runner). On Android those
    textures stay empty; only the renderer reads them, and every byte of the .scmap is still read.
    The preview chunk reports success as it does with a device.
  - *No socket connectors off Windows* (`Common.cpp`): `NET_Init()` already fails there, and the
    connector constructors (Winsock's event model, W2) are left out of the link.
  - *Spatial database without the renderer* (`Mesh.cpp`, `FAF_PORT_MESH_SPATIAL_DB_ONLY`, compiled
    by `MeshSpatialDb.cpp`): the .scmap's wave generators and decals register in it.
  - *D3DX matrix multiply* (`Matrix.cpp`): a portable `Math::mul` with D3DX's contract; not proven
    bit-exact against d3dx9 (W5).

## Running it on a device or the emulator

```sh
python scripts/port/run_runner_android.py --abi x86_64 --replay buildstage/replays-m3/T1-26675870.scfareplay \
    --registry-dump --windows-ref buildstage/replays-m3/runs-m3c-F-s2
python scripts/port/run_runner_android.py --serial <phone> --replay <file> --dry-run   # what it would push and run
```

The script (its docstring has the details) pushes the stripped binaries, the game data the
Windows runner mounts through `init_faf.lua` (3.6 GB, verified by sha256, pushed once) and the
replays to `/data/local/tmp/fafre-runner/`, runs the runner with `FAF_LOWARENA`, pulls the summary,
stdout, engine log, registry dump and logcat into `buildstage/runner-runs/<serial>/<abi>/`,
symbolizes a crash against the unstripped library, and with `--windows-ref` writes a
`.compare.json` (chain, first diverging checkpoint, beat 0, Lua errors, registry). From Git Bash
prefix `MSYS_NO_PATHCONV=1`. `--env FAF_LOWARENA_CHECK=1` turns on the heap check
([lowarena README](../lowarena/README.md#heap-check)).

Since 0.4.0 it also takes `.fafreplay` files (the runner decodes them; the map comes from the JSON
line), has a reference mode for the app, `--host-prefs none` (no `Game.prefs` in the runner's home,
a stale one is deleted, and `fa_path.lua` names `<data root>/vault-reference`, a vault without mods,
as on a phone), and `--write-refs FILE` enters every run that reached its end in the app's reference
table. Generated files are staged under short flat names, so a long `--out-dir` works; a host path
adb.exe cannot open stops the script up front.

## Release 0.4.0: replay input and crash reports

The in-app replay test execs this executable from the APK (`lib/<abi>/libfafrunner.so`) and needs
three things from it that `main.exe` gets from `scripts/perf/convert_replay.py` and the debugger. All
three live in the executable only; `libfafengine.so` and `HeadlessReplay.cpp` are unchanged (the
engine still only loads a `Supreme Commander v1.50.3764` file).

**Replay input** (`ReplayFile.cpp`). A `.fafreplay` is one JSON line and a body: zstd
(`"compression":"zstd"`, the vault, the browser download `https://replay.faforever.com/<id>`, the
Python and Rust clients; frames without a content size, decoded as a stream) or legacy
base64(4-byte big-endian length + zlib) (the Java client's own recordings). The decoder is
[zstd 1.5.7](../../third_party/zstd/README.md) and the system libz; base64 follows Python's
`binascii` (characters outside the alphabet skipped, padding ends the data), so the result is what
the script produces. The body's version `Supreme Commander v1.50.NNNN` gets the digits `3764`, the
same length, nothing else moves (`--as-version 3764`). Caps: 64 MB in, 256 MB out.

| Command | What it does |
|---|---|
| `faf_headless_runner /replayinfo <file>` | prints one JSON object and exits 0 (1 when the file cannot be decoded, with `"ok":false` and `"error"`); no engine is loaded |
| `faf_headless_runner /convertreplay <in> <out>` | writes the engine's `.scfareplay` (through `<out>.tmp` and a rename) and prints the same object plus `"output"` |
| `faf_headless_runner /headlessreplay <file> ...` | a file that is not already a 3764 `.scfareplay` is converted first, in a child process (its allocations never touch the runner's heap), into `<directory of /headlesssummary, else of /log, else .>/<lower-case name>.scfareplay`, and the engine gets that path; the runner prints `[runner] input {...}` (the same object) on stdout |

The object (no player names, titles or chat): `ok`, `error`, `file`, `output`, `format`
(`scfareplay`, `fafreplay-zstd`, `fafreplay-legacy`), `size`, `sha256` (of the file, the key of
the reference table), `id` (`uid`; a number out of range or a string over 18 digits gives `null`),
`map` (`mapname`; when that is empty, as in coop replays, the body's map folder `map_dir`),
`featured_mod`, `featured_mod_version` (the recorded game version, the digits of the body's version
string), `players` (`num_players`, `null` outside 0..1000000), `game_time_seconds`
(`game_end - launched_at`, both finite), `complete`, `header_version` (as recorded),
`decoded_size`, `decoded_sha256` (as decoded), `converted_sha256` (after the rewrite: what
`/convertreplay` writes), `version_rewritten`, `zstd_frames`, `truncated`, `trailing_bytes` (only
when set), and from the body the same parse as the engine's pre-scan: `map_path`, `map_dir`,
`armies`, `command_sources`, `beats`, `sim_seconds` (`beats / 10`), `has_end_game`,
`recorded_checksums`, `checksum_beats`, `scan_error`. Example (the vault's 26675870):

```json
{"ok":true,"file":"26675870.fafreplay","format":"fafreplay-zstd","size":2399,"sha256":"fbb9c0aec784ba62b2050b15e793b7808527e0ac9d0eade1e15d33ce73cfdb19","id":26675870,"map":"scmp_026","featured_mod":"faf","featured_mod_version":3831,"players":2,"game_time_seconds":191,"complete":true,"header_version":"Supreme Commander v1.50.3831","decoded_size":11352,"decoded_sha256":"b7c7af15a059a990557d595fdba47aaa7682eea77ede8a8b0e08c16235c29b05","converted_sha256":"bc4320a2a5cf96e86ef346075c3858b4296f1d826eae7c62547e4885cf105df8","version_rewritten":true,"zstd_frames":1,"map_path":"/maps/SCMP_026/SCMP_026.scmap","map_dir":"SCMP_026","armies":4,"command_sources":2,"beats":465,"sim_seconds":46.500,"has_end_game":false,"recorded_checksums":20,"checksum_beats":10,"scan_error":null}
```

Parity, measured 2026-10-07 with the final 0.4.0 binaries on the API 36 emulator (x86_64 native and
arm64-v8a under ARM translation): `/convertreplay` over all 419 `.fafreplay` files in

**Crash reports** (`RunnerCrash.cpp`). The engine's crash-to-summary filter is Windows-only and an
app cannot read the tombstone of its child, so the runner reports a fatal signal itself (SIGSEGV,
SIGBUS, SIGILL, SIGFPE, SIGABRT, SIGTRAP, SIGSYS; `SA_SIGINFO | SA_ONSTACK`), async-signal-safe, on
stderr, then chains to the action installed before it (debuggerd: tombstone and logcat as before;
the exit status stays 128 + signal):

```
[runner] CRASH sig=11 (SIGSEGV) code=1 (SEGV_MAPERR) addr=0xe29ce510 pc=0x7d35bb8c6770 (libfafengine.so+0xb1d770) lr=0x7d35bb8c6710 (libfafengine.so+0xb1d710) sp=0x7d35c00ff7f0 tid=18275 libfafengine.so base=0x7d35bada9000 build_id=cbb70516dc5aa4ac779517791fa59e2083fb885c runner build_id=0a0f773f03e8aa4d19bf4a396df6095950f6e2df
[runner] CRASH #00 pc 0x7d35bb8c6770 (libfafengine.so+0xb1d770)
[runner] CRASH #01 pc 0x7d35bb8c6710 (libfafengine.so+0xb1d710)
...
```

Offsets are relative to the module's load bias, i.e. ELF addresses:
`llvm-symbolizer --obj=<unstripped libfafengine.so of that build id> 0xb1d770`. Frames from #01 on
are return addresses (subtract 1 on x86_64, 4 on arm64 for the call). `lr` is `-` on x86_64. The
frame walk follows frame pointers and reads the stack through `process_vm_readv`, so a bad frame
ends the walk instead of faulting; at most 32 frames. A signal while another thread is already
reporting only chains. SIGSYS adds `syscall=<nr>` (a call the app seccomp filter blocks). A signal
another process sent (`code` <= 0: `SI_USER`, `SI_TKILL`, `SI_QUEUE`, e.g. `kill -ABRT`) names the
sender instead of a fault address: `[runner] CRASH sig=6 (SIGABRT) code=0 (SI_USER) sender_pid=31936
sender_uid=2000 pc=...` (checked on the emulator, exit 134).

Checked on the emulator with `FAF_LOWARENA=0` T1 (the known C2 truncation): x86_64 and arm64
(translated) both print the report with frames that symbolize to `AddMappedBlueprintOrdinalBits`
(`EntityCategoryReflection.cpp:169`) <- `EntityCategory::Add` <- `ParseEntityCategory` ..., and
debuggerd still writes its tombstone; exit 139.

**References for the app.** `port/android/assets/replay_refs.json`, keyed by the sha256 of the
`.fafreplay` as downloaded, written by `run_runner_android.py --host-prefs none --write-refs` from
the binaries in its `build_ids`:

| Replay (vault) | sha256 of the download | Beats | Game over | Chain (x86_64 and arm64 translated) | First checkpoint differing from Windows |
|---|---|---:|---:|---|---|
| 26675870 (SCMP_026) | `fbb9c0aec784ba62b2050b15e793b7808527e0ac9d0eade1e15d33ce73cfdb19` | 465 | 467 | `4971bbe58c5586a0` | beat 100 (Windows `7e159db290f576f1` on the same converted bytes, Debug\|Win32 M3c build) |

The vault copy decodes to 11352 bytes against 11350 for the local recording M3c used (two more
bytes at the end); the chain is the same as M3c's (`4971bbe58c5586a0` on both ABIs, also without

**In the app** (the launcher's Replay test, [docs/port/android.md](../../../docs/port/android.md#replay-test);
emulator results in [headless-replay.md](../../../docs/port/headless-replay.md#in-app-replay-test-release-040)):
the APK execs `nativeLibraryDir/libfafrunner.so`, which the linker puts in its "system" namespace
(not "unrestricted" as under `/data/local/tmp`) and which inherits the app's seccomp filter and
`untrusted_app` domain. On the emulator that changes nothing for the runner: the vault T1 gives
`4971bbe58c5586a0` in the app with the x86_64 APK and, under translation, with the arm64-v8a APK;
the crash report and debuggerd's backtrace both reach the run's files (the app may read its own
uid's crash log lines).

Against M3c's binaries the engine library differs only by the shim's MapViewOfFile fallback

On the API 36 emulator the runner plays all four M3a replays (T1-T3, R4) to the end with the low
arena as native x86_64, and T1 as arm64 under the ARM translation: exit 0, game over at the
replay's last beat, no trap, the same checkpoints on repeated runs. Results and the comparison
with Windows are in [headless-replay.md](../../../docs/port/headless-replay.md#android-runner-m3c).
Two engine bugs had to be fixed for it (guarded, Windows unchanged; found with the low arena's
heap check):

- `gpg/core/algorithms/Cluster.cpp`: the HaStar cluster cache released its boost control block
  through raw vtable slots 1 and 2 and `long` counts, which is the MSVC ABI. Under the Itanium ABI
  slot 1 is the deleting destructor, so the release freed the block, leaked the cache, and then
  decremented the weak count in the freed block (8 bytes further on in LP64): heap corruption at
  every `PathTables` teardown. T1 then aborted in `dlfree` while the sim's Lua state was closed,
  after the game was over. Off MSVC the release uses the storage's own counts,
  `SpCountedImplPDisposeClusterCacheImpl` and `operator delete`.
- `lua/LuaObject.cpp`: the io library's `WrapFile` type put two out-pointer functions
  (`RRef* f(RRef* out, ...)`, the MSVC x86 shape of a by-value `RRef` return) into RType's by-value
  `new_ref`/`ctor_ref` slots. On x86-64 and AArch64 a 16-byte trivially copyable `RRef` is returned
  in registers, so `ctorRefFunc_(payload)` wrote 16 bytes through whatever the second argument
  register held, for each of the three io files of every Lua state. Off MSVC the slots get by-value
  wrappers. The stray write was also what Scudo reported as a corrupted chunk header in Lua's
  start-up with `FAF_LOWARENA=0`, and what stopped the arm64 heap-check run in `LuaOpenIo`.

The sim reads uninitialised heap memory (the `Unit::UpdateBlipsInRange` gate of
[headless-replay.md's known issues](../../../docs/port/headless-replay.md#known-issues)), and on
Android that changes checkpoints: filling every new block with `0xff` (`FAF_LOWARENA_FILL=0xff`)
changes T3's chain from beat 6150 and R4's from beat 3600, while `0x00` and `0xcd` (bits `0x30`
clear, as in the gate's test) give the normal chains. The heap check (its `0xdd` fill) and the
stray `WrapFile` write before its fix land in the same other class. Runs with the same binary and
environment are identical.
