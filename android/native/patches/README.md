# The engine's and SDL's files the Android build compiles changed

Each `<path>.patch` is a `git diff` of the engine file `<path>`, or of a dependency's file under `dependencies/`,
applied to a copy at configure time (`../cmake/FafAndroidOverlay.cmake`, `../README.md`). The repository's files
stay as they are.

| File | Change | Why there is no other way |
|---|---|---|
| `src/gpg/gal/backends/vulkan/DeviceVulkan.cpp` | The swap chain takes R8G8B8A8 where the window has no B8G8R8A8; copies between the two orders blit, readbacks swap red and blue; the swap chain's usage is what the surface supports; its composite alpha is one the surface has; its pre-transform is the identity; a device without BC textures comes up and holds BC1-3 textures as R8G8B8A8: uploads decode them on the CPU (`src/gal/BlockCompressionAndroid.cpp`, WARP's decode), readbacks compress them again; the engine still sees the BC format. The log says which way BC textures go (the game's report takes the line), and `FAF_VULKAN_BC_ON_CPU=1` takes the CPU's way on a GPU with BC too, which tries the phones' way on the emulator (the game activity's `bcOnCpu` extra) | Android's window surfaces have no B8G8R8A8 and only INHERIT for composite alpha, and phones' GPUs mostly lack BC (the Galaxy S22's Xclipse 920 has ETC2 and ASTC); the UI's texture sheets are BC3 textures the engine fills itself, which no codec sees. A phone's panel is portrait: the engine draws upright, and with the surface's current transform the compositor would show the image turned, on a landscape screen also squeezed. Upstream's code refuses a surface without B8G8R8A8_UNORM ("the window surface has no B8G8R8A8_UNORM format") |

Not Android's own, candidates for the engine |

| `src/moho/ui/CUIWorldViewEvents.cpp` (a finger's UI, `../../TOUCH_UI.md`) | `UI_TapTarget`: where a tap beside a small control goes, walking the controls; `UI_GhostWaitsAt`, `UI_GamePlaying`: what the app's pointer and its buttons go by | They need the control tree, the capture stack and the world view, which are this file's; the choice among the controls is `include/TapTarget.h`, which has tests |
| `src/moho/ui/UiMisc.cpp`, `CUIWorldViewEvents.cpp`, `CMauiMovie.cpp` (the cursor, the movies, placing a building) | `ui_DisableCursorFixing` is on, and FAF's Lua cannot turn it off; a movie that cannot play counts as loaded, so it is over as soon as it is played, and asking its length is safe; a double click of the left button is a press, `UI_PlacingBuilding` tells the app that a ghost waits, `UI_WorldViewAt` what is under a place, and `UI_CancelBuildDrag` gives up a line of buildings being drawn | The middle button's camera drag holds the cursor still and takes relative moves (on POSIX the window layer's relative mouse mode), and Android's pointer and fingers say where they are. | `src/moho/misc/StartupHelpers.cpp` (`FILE_Dir`, a game's save) | A path that starts with `/` is a system path | On Windows such a path is one of the game's own and a system path has a drive. Here each save stopped at "Saving game...", with a Lua error from `FILE_Dir` that nothing shows |
| `src/moho/net/CNetUDPConnector.cpp` (its end) | The connector is deleted when its thread ends, as the binary's `shared_ptr` does (`0x00489F90` takes it by value, and its destructor closes the socket), and closes its event (`platform::net::CloseSocketEvent`); the deleter does so only once `fa::thread` has started; `Pull` ends under the lock; `Destroy` forgets the game's event. It counts the connectors whose socket is open, from its thread's start to its deletion (`NET_OpenUDPConnectors`) | With upstream's deleter, which does nothing, a lobby left a bound socket behind, and the next lobby on that port found it taken. A thread that does not start throws in the constructor, whose unwinding drops the last owner: that one must not delete what is being constructed. Once `Pull` has cleared `mIsPulling` on a closed connector its thread may delete it, so the rest of `Pull` holds the lock it needs for that (FAF's lobby destroys itself in `Pull`'s dispatch). On Windows `SetEvent` on a closed handle fails; the POSIX layer's `CloseHandle` deletes the object, and the game closes its event right after `Destroy` while the thread may go on handling packets. The count is what the app's `NetworkGameService` goes by: a network lobby or game has a connector, the LAN screen's search for games a datagram socket, a skirmish neither. Not Android's own, candidates for the engine (but the count) |
| `src/moho/net/SPeer.cpp`, `CLobby.cpp` (`LOBMSG_NewPeer`) | The address is a `std::uint32_t` on the wire | The fields are written and read by their C++ type, and `u_long` is 4 bytes in the Windows game and 8 on LP64 POSIX (`src/platform/posix/win32/winsock2.h`: Android's 64-bit ABIs and the Linux client). The host sends the message when a player joins, of each player in the lobby to the newcomer and of him to them: after the name the address, the port and the uid, and the reader does not look for bytes left over. A Windows sender puts 10 bytes after the name, where an LP64 reader asks for 14, so the read of the uid ends early (`PrematureEOF`), `ReceiveMessage` drops the message and that client never connects to the player (Draiget's review of #450). A Windows reader of an LP64 sender takes the address right, then two of its four zero upper bytes as the port, 0, and the other two with the port as the uid, leaves the real uid unread, and tries the player on port 0. It is the only such field of the protocol (`tests/net`, which pins it). Not Android's own, a candidate for the engine |
| `src/moho/net/CLobby.cpp` (`~CLobby`) | Drops the lobby's linkages before `connector->Destroy()` | From `Destroy` on the connector's thread deletes the connections and their linkages, while this thread, in the destructors after this body, unlinks the same rings, with no lock in common. All three: `mEjected` alone counts as having queued every beat, and the issue thread issues one beat each pass once the game is over. The request: FAF's disconnect panel opens for a client that has gone and that those still in have not ejected, as `Replay` over a replay did. A replay's client takes all of it as well, or the file's beats run on, past a sim that is over. Not Android's own |

`src/gpg/gal/backends/vulkan/RayTracingVulkan.cpp` is compiled from the overlay as well, unchanged: it
includes its patched header, `DeviceVulkan.h`, by its bare name, which would find the unpatched one
