# The engine files the Android build compiles changed

Each `<path>.patch` is a `git diff` of the engine file `<path>`, applied to a copy at configure time
(`../cmake/FafAndroidOverlay.cmake`, `../README.md`). The repository's files stay as they are.

| File | Change | Why there is no other way |
|---|---|---|
| `src/gpg/gal/Device.cpp` | The device factory and `SupportsVertexTextureFormat` without the Direct3D 9 to 12 cases and their includes | The factory names every backend's class; Android has the Vulkan backend alone |
| `src/gpg/gal/backends/vulkan/DeviceVulkan.cpp` | The swap chain takes R8G8B8A8 where the window has no B8G8R8A8; copies between the two orders blit, readbacks swap red and blue; the swap chain's usage is what the surface supports; its composite alpha is one the surface has; its pre-transform is the identity; a device without BC textures comes up and holds BC1-3 textures as R8G8B8A8: uploads decode them on the CPU (`src/gal/BlockCompressionAndroid.cpp`, WARP's decode), readbacks compress them again; the engine still sees the BC format | Android's window surfaces have no B8G8R8A8 and only INHERIT for composite alpha, and phones' GPUs mostly lack BC (the Galaxy S22's Xclipse 920 has ETC2 and ASTC); the UI's texture sheets are BC3 textures the engine fills itself, which no codec sees. A phone's panel is portrait: the engine draws upright, and with the surface's current transform the compositor would show the image turned, on a landscape screen also squeezed |
| `src/gpg/gal/backends/vulkan/DeviceVulkan.cpp`, `DeviceVulkan.h` (the surface) | `TestCooperativeLevel` lets go of a surface that went or changed its size, or a swap chain that failed, and takes the next surface: a new `VkSurface` and swap chain, whose images the back buffer target takes. Until then it answers 2, what would draw on the back buffer draws nowhere, as it does after a failed acquire, and the engine's objects stay; only a new size goes through 1 and `InitContext`, with the head at that size first: a head has the surface's size, whatever the engine asks for (`CreateSwapChain`; `Setup` checks the formats before it, as that takes the engine's context whole). `Reset` leaves a surface that went to `TestCooperativeLevel`. `Setup` waits for a surface, and for the next one if it goes before there is a swap chain. `Present` shows no image that nothing drew, which stays for the frame that draws it, and says when a frame with draws went out | An activity's surface goes when it goes to the back, nothing may use it after `surfaceDestroyed` returns (`Win32Android_SetScreenSurface`), it can change its size in place, also between the program's start and its window (the activity's first surface can be the one before it turned), and a window takes one `VkSurface` at a time; a Windows program's window stays. `CD3DDevice::Paint` presents before it renders, so a new swap chain's first image holds nothing |
| `src/gpg/gal/backends/vulkan/ResourcesVulkan.cpp`, `ResourcesVulkan.h`, `DeviceVulkan.cpp`, `DeviceVulkan.h` (the draws) | A dynamic buffer's copy in upload memory holds what is locked and what draws read (`PrepareDraw` works it out, an indexed draw's from its indices, and from all of the buffer where `Device::ReleaseBufferCopy` freed the indices' CPU copy), with the last values, where it held the whole buffer | The UI's batches lock 0x8000 vertices' buffer for a few each, many times a frame: the menu ran at 10 fps on the emulator. Not Android's own, a candidate for the engine, with `BufferStorageD3D12` |
| `src/gpg/gal/backends/vulkan/VulkanCore.cpp`, `DeviceVulkan.cpp` (`CheckCommandBuffer`, `AttachSurface`) | The program ends (`gpg::Die`) on `VK_ERROR_DEVICE_LOST`, when a command buffer cannot be got, begun, ended, submitted or waited for, and when a surface that is there refuses a swap chain for 5 s | `CD3DDevice::Paint` catches the error and goes on, as for Direct3D 9, whose device can be reset; a `VkDevice` cannot, and the next frame would go on with a command buffer that has ended |
| `src/gpg/gal/backends/vulkan/DeviceVulkan.cpp`, `DeviceVulkan.h`, `GpuDrivenVulkan.cpp` (Vulkan's rules) | A rendering scope that loads an attachment in the same layout waits for the store before it (`BeginRendering`); readbacks have a barrier to the host; a pipeline's depth bias clamp is 0 where the device lacks the feature, and enabled where it has it; a pixel shader's input no vertex shader writes takes the device's last location, not 31; GPU-driven drawing is off, with a warning, where a stage has fewer storage buffers than its set has, and its compute where a work group is smaller than `CompactIconsCS` has it: the engine's paths then do without (`GpuPathEnabled`). A warning says when a stage allows fewer textures or samplers than the effects' layout has | Desktop GPUs and the emulator forgive these, a tile-based GPU or one at Vulkan's minimum limits need not. Not Android's own, candidates for the engine |
| `src/moho/ui/UiMisc.cpp`, `CUIWorldViewEvents.cpp`, `CMauiMovie.cpp` (the cursor, the movies, placing a building) | `ui_DisableCursorFixing` is on, and FAF's Lua cannot turn it off; a movie that cannot play counts as loaded, so it is over as soon as it is played, and asking its length is safe; in build mode a finger's press (`MOUSEEVENTF_FROMTOUCH`) only puts the building's ghost, a double click of the left button is a press, `UI_PlacingBuilding` tells the app that a ghost waits, and `UI_WorldViewAt` what is under a place | The middle button's camera drag holds the cursor still and takes relative moves, and Android's pointer and fingers say where they are. Screens wait for a movie's end, and an import may have no movies: the first visit to the campaign waited in black for ever. A finger has no hover: nothing shows where a building would go until the finger is down, and then the finger covers it. The app's word is a frame old or more, so the press itself has to say whose it is |
| `src/platform/posix/Win32Shim.cpp`, `src/moho/audio/SofdecRuntime.cpp` (the movie's path) | `Win32Android_DiskPath` gives a path as the disk has it, and `mwPlyStartFname` gives the movie player that | `CMovie`'s path is the file system's, with backslashes and in lower case. The player's metadata read and FFmpeg open the file themselves, past the POSIX layer that takes such a path |
| `src/moho/audio/SofdecRuntime.cpp` (the upload) | `mwPlyGetCurFrm` hands out no frame while the texture has it | The game draws faster than a movie runs, and each frame it drew copied the whole picture, 7.5 MB at 1824x1024, twice on its way to the GPU. Not Android's own, a candidate for the engine |
| `src/moho/movie/sfd/IndependentSfdBackend.cpp` | A due frame leaves the queue at once, not only after the decoding; the worker decodes without the player's lock; it keeps a quarter of a second ready, not half | Late frames piled up behind what is kept ready until the queue's limit ended the movie ("Excessive SFD stream interleave"): 17 frames at 1824x1024, which a slow CPU or a stall of 100 ms reaches. The game's thread asks for the current frame under the lock each frame and waited out each decode. Half a second of frames is 120 MB on a phone. The first two are not Android's own, candidates for the engine |
| `src/gpg/core/diagnostics/posix/DiagnosticsPosix.cpp` | A fatal signal goes from the crash report to the handler that was there first, debuggerd's, instead of the default action; the report is written on a thread of its own, which the faulting thread waits for at most 3 s, and a fault there ends only that thread; `faf_crash_latest.txt` is written first, so it holds what a report that stopped has; the crash report and `faf_diag.log` go to HOME; the exception filter's report gives the fault for a reason | A phone has no adb, so a crash's stack has to be in what the app collects: debuggerd writes the tombstone only from its own handler, which this file's handlers displace, and the file writes beside the executable, which for an app is `/system/bin/app_process64`. On the faulting thread a fault in the report, a thread's small signal stack or a lock the fault holds would cost the tombstone |
| `src/moho/misc/StartupHelpers.cpp` | `USER_SavePreferences` opens its stream with `/` for `\` | The path has Windows' separators, which the engine's POSIX layer converts in its Win32 functions; a C++ stream takes them for part of a file name, so `Game.prefs` was never written |
| `src/gpg/gal/backends/vulkan/VulkanLoader.cpp` | Opens `libvulkan.so` | The loader names `vulkan-1.dll`, and the engine's POSIX `LoadLibraryA` is a plain `dlopen` |
| `src/gpg/gal/D3D9Utils.h` | Includes `<d3d9types.h>` where the stand-ins provide it | The gal interfaces take a `D3DVIEWPORT9`; the header includes the type on Windows only |
| `src/moho/render/ID3DTextureSheet.h` | The same, instead of its own `RECT` and `D3DLOCKED_RECT` | Its own `RECT` clashes with the one the engine's POSIX `Windows.h` defines, which the client's files include as well |
| `dependencies/boost_1_34_1/libs/thread/src/mutex.cpp` | `boost::mutex` is recursive | On Windows boost 1.34's mutex is a critical section, which the thread that holds it may take again, and the engine's code relies on that (`STAT_GetLuaTable` holds a stat's lock while `StatItem::ToLua` takes it again, every UI frame); a POSIX mutex deadlocks there |
| `src/moho/net/CLobby.cpp` | `GetPeerStyle` takes the shared `SCR_UserLuaInitSet` and `SCR_ExpectExactArgs`, as the file's other functions do | Upstream's aea69b0b names the two helpers that 8f9bc568 had just removed from the file, so it compiles for no platform. This patch goes when upstream fixes it: it then no longer applies |
| `src/moho/console/ClientConCommands.cpp` | `EFX_CreateEmitterWindow` says in the log that the build has no emitter editor; the selection helper only it used goes | The command creates the editor, `WEmitterWx`, a wx tool window that wx-lite leaves out (`../WX_LITE.md`); a stand-in for its constructor would need the whole frame class |

`src/moho/render/ID3DTextureSheet.cpp` is compiled from the overlay as well, unchanged: it includes
its patched header by its bare name, which would find the unpatched one next to it.
